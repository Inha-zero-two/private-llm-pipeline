# 실행 모니터 (#78)

기존 화면의 **모니터 창 열기**로 같은 앱·포트의 `/monitor`를 연다. 기존 화면은 질문·동의 입력·중지·최종 답변·모델 비교를 맡고, 모니터는 현재 실행의 과정과 프론티어 요청·응답을 읽기만 한다.

## 표시와 전환

- 왼쪽은 채팅 이름·질문·실행 ID·현재 상태·실행 경과와 한 회차의 요청·응답이다. 공통 좌우 화살표로 두 본문을 함께 바꾼다. 질의가 0회 또는 1회이면 화살표를 표시하지 않는다.
- 오른쪽은 기존 실행 로그의 질문·상태·단계·응답 수신 횟수·종료 사유·오류 내용/코드/단계·공개 동의 대기 항목을 유지한다. 이벤트와 공개 동의 기록은 탭으로 나눈다. 동의 기록에는 사용자 응답, 항목 이름·값·허용/거절, 취소 내역을 표시한다.
- 전체 화면은 뷰포트 안에 고정하고, 긴 요청·응답·실행 상세·이벤트·동의 기록만 각 영역 안에서 스크롤한다. 상단 네비게이션이나 단계별 실행 카드는 두지 않는다.
- 프론티어 질의 **시도**와 성공 응답 **수신**을 구분한다. `uncertain`은 실행 중에는 응답 대기, 종료 후에는 결과 불확실로 표시한다. 실패한 요청문도 유지한다. 중지는 실행 종료 사유와 함께 표시한다.
- 최신 회차를 보고 있었다면 새 회차로 이동한다. 이전 회차를 읽고 있었다면 유지하고 `새 질의 도착 · 최신 보기`를 표시한다.
- 로그는 기본적으로 최신을 따라가며, 위로 스크롤하면 멈춘다. `최신으로`로 다시 따라갈 수 있다. 필터는 전체/로컬/외부 질의이며, 질의 버튼으로 관련 요청·응답을 선택한다.

실행 경과는 `startedAt`부터의 벽시계 시간이며 동의 대기를 포함한다. 이벤트의 경과 시간은 `createdAt − startedAt`이다. 기존 조작 화면의 최종 답변 소요 시간은 계속 동의 대기·해석 시간을 제외하므로 두 값은 용도가 다르다. 시각이 없는 과거 이벤트는 임의로 추정하지 않고 `—`로 표시한다.

## 실행 ID 전달과 복원

실제 서버 모드에서는 질문 시작 응답으로 받은 `chatId`·`runId`만 `pipeline.monitor.target.v1`에 보관하고 같은 브라우저의 모니터에 전달한다. 채팅 선택이나 과거 질문 선택으로 대상을 바꾸지 않는다. A 실행 도중 B 채팅을 열어도 A를 유지하고, 다음 실행이 시작될 때만 새 대상으로 전환한다. 새 실행에서는 탭·회차·로그 따라가기·본문 스크롤과 실행 정보를 초기화한다. 실행 종료 후 마지막 기록을 유지하며, 대상을 받은 적이 없으면 대기 화면이다.

- 창 간 통신은 `BroadcastChannel`과 `storage` 이벤트를 사용한다. 저장소에 질문·응답·동의 본문을 복제하지 않는다.
- 창 URL에도 알려진 실행 ID를 전달해 저장소가 제한된 경우와 새로고침을 보완한다. 알려진 ID를 복원할 뿐 서버에서 현재 실행을 자동 탐색하지 않는다.
- 모니터는 API-03(채팅 상세)과 API-11(실행 상세)을 조회하고 API-06(SSE)을 독립적으로 구독한다. 이벤트 ID로 중복 로그를 제거하고 종료 후 API-11의 최종 상태로 맞춘다.
- 연결 실패는 실행 오류와 별개로 표시하고 마지막 화면을 유지한다. EventSource의 자동 재접속과 상세 조회 재시도로 기록을 복원한다. 실행/채팅이 삭제되어 404이면 재시도를 멈춘다.
- 모니터가 닫히거나 대상을 바꾸면 해당 조회·구독만 해제한다. 중지·질문 전송 API를 호출하지 않는다.
- 실행 고정, 현재 실행 탐색 API, 탭 제목 변경·시스템 알림, 모니터 안의 동의 입력은 없다.

서버 데이터가 기준이다. 목업의 설명용 질의 제목·시간·오류 코드는 실제 실행에서 만들지 않으며, 프론티어 오류를 로컬 답변으로 복구하는 기존 `offline` 정책도 변경하지 않는다. 과거 기록에는 새 질의 수명 이벤트가 없을 수 있지만 API-11의 요청·응답·상태는 조회할 수 있다.

## 코드와 SSE

`web/src/monitor/`에 창 간 전달(`bridge`), 읽기 전용 서버 구독(`client`), 이벤트 변환(`model`), 데모 변환(`demo`), React 연결(`useMonitor`)과 화면을 둔다. `App.tsx`는 실행 시작·복원 시 ID를 전달하고 버튼을 제공한다. `/monitor`에서는 기존 앱을 마운트하지 않아 모델 비교나 실행 조작을 시작하지 않는다.

API 주소는 추가하지 않았다. API-06의 화면용 기록 이벤트에 저장 시각 `createdAt`을 추가했고, `step.stage`로 처리 위치를 전달한다. 프론티어 호출은 저장된 `queryId`·회차를 가진 다음 두 이벤트로 보완한다.

| 이벤트 | 필드 | 시점 |
| --- | --- | --- |
| `frontier_request` | `queryId`, `round`, `request`, `createdAt` | 누출 검사를 통과한 질의를 저장한 뒤 외부 호출 직전 |
| `frontier_result` | `queryId`, `round`, `status` (`ok`/`failed`), `answer` (문자열/null), `createdAt` | 질의 결과를 저장한 뒤 |

기존 `frontier` 성공 이벤트는 기존 클라이언트 호환을 위해 유지한다. 새 모니터는 새 수명 이벤트와 상세 조회를 사용하므로 중복 표시하지 않는다. 내부 `llm_call`·`run_error` 기록은 여전히 공개 SSE로 보내지 않는다. API-11의 각 질의에도 `createdAt`을 제공한다.

## 데모와 확인

`npm run dev:demo`에서도 모니터를 사용할 수 있다. 데모 실행은 새 식별자로 구분하고, 원본 화면이 관측한 단계·응답·동의 상태를 채널로 전달한다. 데모 본문은 서버나 영구 저장소에 쓰지 않으며, 원본 화면을 열어 둬야 한다. 모니터를 새로고침하면 열려 있는 원본 화면에 마지막 데모 스냅샷을 요청한다. 데모가 임의의 서버 오류 코드를 만들지는 않는다.

실제 비교 패널까지 확인하려면 앱 서버를 켜고 `npm run dev`로 실행한다. 기존과 같이 데모 모드에서는 모델 비교 패널을 숨긴다.

확인 항목은 요청 시작/성공/실패, 대기·응답·취소 동의 이력, 회차 자동 추적/이전 회차 유지, 이벤트 중복 제거, 알려진 실행의 연결 복원과 해제이다. 서버 테스트는 모델 대역을 사용하며 프론트 테스트는 실제 `model`·`client`를 가짜 EventSource와 함께 검사한다. 실제 모델에 대한 시연은 별도 수행한다.

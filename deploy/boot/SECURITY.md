# 새 LLM 서버 연결 보안 검토

2026-10-28 구현 이후 코드·자동 테스트·실제 서비스 응답을 확인했습니다.
검토 범위는 어댑터의 원격 연결, GPU 부팅 경로, Caddy, 인증서·DNS 자동화와 키 관리입니다.
인증키를 가진 신뢰하는 팀원이 사용하는 API를 전제로 합니다.

## 발견 후 수정한 사항

- 원격 `http://` URL에 Bearer 키가 실릴 수 있던 경로를 제거했습니다. HTTPS만 허용하고
  잘못된 authority·포트·userinfo·쿼리·제어문자는 키를 읽기 전에 거부합니다.
- 전역 관리 경로가 프록시를 통과하던 동작을 좁혔습니다. `/slots` 및 하위 경로, `/metrics`,
  `/lora-adapters` 및 하위 경로, `/props` 변경 메서드는 외부에서 404입니다.
  UI와 GET `/props` 및 추론 경로는 유지하고 기존 서버의 API 키 인증을 사용합니다.
- llama.cpp의 `--api_key`, `--n_gpu_layers` 등 underscore 별칭이 launcher 검사를 우회하던
  문제를 고쳤습니다. 검사할 이름을 upstream처럼 정규화한 후 같은 규칙을 적용합니다.
- 인증서 다운로드가 환경 HTTP 프록시를 사용하지 않도록 했고, 외부 명령의 환경에서는
  Porkbun API 키를 제거했습니다. API 응답·키 값이 오류 로그에 포함되지 않습니다.

## 확인한 방어

- 기본 주소 `https://satisshin.top:4000`에서 공인 CA·호스트명 검증을 켜고 실호출 성공.
- HTTPX의 환경 프록시와 자동 리다이렉트 사용 금지. 일반·스트리밍의 302에서도 키 전달 없음.
- 기존 키 4개 성공, 익명·잘못된 키는 401. 키는 값을 변경하지 않고 재사용.
- 외부 관리 경로·인코딩된 우회 경로·POST `/props`의 404와 GET `/props`·추론 정상 동작.
- 내부 모델 `127.0.0.1:4001`, Caddy 관리 `127.0.0.1:2019`. 이전 LAN 8080 리스너는 없음.
- 미국 LA 한 노드에서 공개 HTTPS 200, TCP 22·4001·2019는 연결 시간 초과.
- GPU 미감지 시 모델 미실행, 30초 재시도. 모델 장애와 독립적인 HTTPS 503 응답 및 복구 확인.
- 인증서 신뢰 체인·호스트명·유효기간·개인키 일치 검증 후 원자적 교체. 실패 시 이전 파일 유지.
- TLS 키 root:caddy 0640, API 자격증명 root:root 0600, LLM 키 shin-pi:shin-pi 0600.
- API 키는 `satisshin.top` 하나로 제한. 업체가 묶어 둔 도메인 관리 권한을 사용자 승인 후 부여했고
  구매·충전 등 불필요한 권한은 제외. 유동 IP 대응을 위해 호출 IP 제한은 미사용.
- DDNS는 두 고정 HTTPS 출처가 같은 공인 IPv4를 반환할 때만 기존 루트 A 하나를 수정.
  같은 IP·모호한 레코드에서는 쓰지 않으며 생성·삭제를 하지 않음. 적용 후 재조회로 검증.
- DNS 자동화는 DynamicUser와 제한된 sandbox로 실행. 인증서 작업의 쓰기는 TLS 저장 경로로 제한.
- 실제 API 키·개인키·번들·배포 묶음은 Git에서 제외. API 키의 전송용 임시 파일 제거.

## 검증의 한계와 운영 조건

코드 검토와 실행한 검사에서 추가 차단급 문제를 발견하지 못했습니다. 모든 종류의 취약점이
없다는 보장은 아니며 OS·커스텀 NVIDIA 드라이버 전체나 독립 침투 테스트를 수행한 것은 아닙니다.

현재 Caddy는 Debian 보안 패키지 `2.6.2-12+deb13u1`입니다. 요청 본문 크기·호출량·사용자별
쿼터 제한은 추가하지 않았습니다. 2.6.x에는 본문 제한의 413을 프록시가 502로 바꾸는
[upstream 결함](https://github.com/caddyserver/caddy/issues/5652)이 있어, Caddy 업데이트 시
8MB 본문 제한과 올바른 413 응답을 함께 시험하는 것이 남은 개선입니다.
API 키가 유출되면 GPU 요청이 남용될 수 있으므로 공개 익명 서비스나 불특정 다수 대상 운영은
별도의 쿼터·호출량 제한 없이 확장하지 않습니다. 키 변경과 SSH 인증 정책은 운영자가 관리합니다.

실제 IP 변경·인증서 재발급을 강제로 일으키지는 않았습니다. 현재 API 실호출은 동일 IP·동일
인증서로 성공했고, 변경·실패·rollback 분기는 합성 데이터와 모의 호출로 시험했습니다.
서비스의 자동 시작 등록과 GPU 확인을 통한 재시작은 확인했으며 OS 전체를 재부팅하지는 않았습니다.
